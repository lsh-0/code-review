# Architecture Review: code-review

## Essence

**A local GUI for leaving line-anchored comments on a branch-vs-main diff, persisted to a JSON file that an AI agent can read and edit back.** The differentiator over GitHub/Bitbucket is the last clause: the review state is a plain, agent-addressable file, enabling an async review→fix→review loop without a server.

The project is small (~3,400 hand-written LOC excluding tests and the 37k-line GopherJS build artefact), healthy, and unusually well-tested. This is not a codebase in trouble. The findings below are about distillation, not rescue.

## Structure

Four Go modules in a workspace, split by GopherJS's compilation boundary, not by domain:

- `model/` — pure domain (`Review`, `FileDiff`, `Comment`, `MarkedFiles`) plus pure aggregation logic. Compiled by **both** native and GopherJS. This is the shared kernel and it is the best-factored part of the project.
- `backend/` — native-only (`//go:build !js`): git shell-outs, diff parsing, JSON persistence, file watcher, and the Wails `App` with ~25 bound methods.
- `frontend/web.go` — GopherJS-only (`//go:build js`): 1,932 lines of imperative DOM construction.
- `assets/` — embeds `index.html`/`style.css` and the compiled `review.js`.

Control flow is sound: `main` → `startup` → one `RecomputeDiff` (the single `git diff` path) → event-driven bridge calls. Dependency direction is correct — `model` depends on nothing, both ends depend on `model`. The recent `RefreshState`-split work (visible in `gitquery.go`'s comments and the openspec archive) deliberately separated the diff axis from the state-reload axis; that was the right call and it shows.

**The one structural problem: `frontend/web.go` is a 1,932-line single file building the entire UI through `doc.Call("createElement", …)` string-keyed DOM calls.** Every element, class, and listener is hand-assembled in Go that reads like assembly for the DOM. This file is half the hand-written code in the project and concentrates nearly all of its incidental complexity.

## Proposed architecture: collapse the GopherJS frontend to plain ES modules

This is the consequential finding. **GopherJS is the project's largest source of incidental complexity and it buys nothing the essence requires.**

What GopherJS currently costs:
- A 37k-line compiled `review.js` shipped in the binary — most of the asset weight, working directly against the stated "small and self-contained" goal.
- A whole-toolchain dependency (`./manage.sh setup` installs Go 1.19.x *and* GopherJS *and* Wails) and a build step that compiles Go-to-JS.
- The `callBackend` reflection-and-`interface{}` bridge, the `*js.Object` ceremony at every line, the `js.Undefined`/`nil` double-guards repeated dozens of times, and a forced module split (`//go:build js` vs `!js`) that exists *only* to keep GopherJS and native code apart.
- A frontend that cannot use any of the browser/JS ecosystem and must hand-roll DOM diffing (`patchLineThread`, `setFileStatusPill`, the `data-line` attribute scheme) because it has no framework.

What it buys: type-sharing of `model.Comment` across the boundary. But the boundary is already JSON strings in both directions — every bound method returns `(string, error)` and the frontend `json.Unmarshal`s it. The types are re-declared on the JS side anyway (`DiffFile`, `DiffHunk`, `DiffLine`, `commentMutationResult` all appear twice). So the shared-type benefit is largely notional; the wire format is JSON regardless.

**Shape of the alternative:** delete the `frontend/` Go module and `assets/review.js`. Write the frontend as a small hand-authored ES module (or one lightweight no-build library) calling the Wails-generated `window.go.main.App.*` bindings directly — which already exist (`backend/frontend/wailsjs/`). The `model` package stops being dual-compiled; it becomes native-only and simpler. The `go.work` drops from four modules to two (`backend` + `model`), and the `js`/`!js` build tags vanish from the codebase entirely.

**What it removes:** one of four modules; ~1,900 lines of `*js.Object` Go; the GopherJS toolchain dependency and its build step; the 37k-line artefact; the `callBackend` reflection bridge; the duplicated type declarations; every `//go:build js` tag. **It sharpens the essence** — "small, self-contained, fast to start" — by removing the single biggest thing standing between the project and that goal.

**Honest about scale:** this is a *rewrite of the frontend*, not a refactor. The 1,900 lines of DOM logic must be re-expressed in JS. The wager is that hand-written JS doing the same DOM work is meaningfully shorter (no `js.Object` boxing, native event handlers, real template literals instead of `createElement` chains) and that the loss of compile-time type-sharing is nearly free because the boundary is already JSON. If the GopherJS choice was made to avoid writing JavaScript at all, that is a preference to weigh — but it is being paid for in toolchain, binary size, and the project's least pleasant file.

## A second, smaller reduction: the dual-state diff cache

`RecomputeDiff` builds a `fileContentCache` and parses every changed file's hunks, but `GetDiffFiles` then strips hunks to metadata and the frontend re-fetches them one file at a time via `GetFileDiff` — re-marshalling from the *already-parsed* `a.diffFiles`. The lazy-load was added to cut startup transfer cost, which is real, but the result is that hunks are parsed eagerly, discarded over the bridge, then shipped piecemeal. The data is already in memory; only the *transfer* is lazy. This is fine, but note it is an optimisation for the Wails JSON bridge specifically — under the proposed frontend it may simplify, since a direct binding can stream the parsed structure without the metadata/full split.

## Reductions and features to cut

- **`open.go` / `BrowseFile` (`xdg-open`)** overlaps conceptually with the planned `git difftool` integration (TODO: uncommitted-change banners). Two ways to "open a file externally" is one concept modelled twice. Pick one — `git difftool` is the more useful, since it honours the user's configured diff tool and is the only one that can show a *diff*.
- **The legacy `MarkedFiles` bare-path migration** (`UnmarshalJSON` + the empty-`Blob` backfill path in `EvictChangedMarks`) is dead weight the moment no old state files remain. It is correct and well-tested, but it is vestigial-by-design. Worth a dated note to delete it once the install base has rolled over.
- **TODO items pulling away from the essence.** "Import review feedback from Bitbucket and GitHub" makes the tool a multi-platform PR client — a different, larger product than "local diff annotator with an agent loop." It is the one planned item that risks diluting the essence; weigh it against that before building. By contrast, the *CLI for agents* TODO pulls directly *toward* the essence (it replaces hand-editing JSON, the riskiest part of the agent loop) and is the highest-value planned work.

## Tests and performance

**Tests are the strongest part of the project.** ~110 tests, and they read as a specification: `FileCommentStatus`, `EvictChangedMarks` (four cases — changed/deleted/legacy/unchanged), the expand-state geometry (`GapExhaustedWhenFrontiersCross`, `StepRangeClampsToSiblingFrontier`), and the state-path hashing all pin *requirements*, not implementation. The design pays off here: because the hard logic was pushed into pure functions in `model` and small helpers in `backend`, it is testable without git or a DOM. This is the payoff of the functional factoring and it is visible. No disposable-test smell.

One altitude gap, caused entirely by the architecture: `frontend/web.go`'s 1,900 lines of DOM assembly are effectively untested (`web_test.go` is `//go:build js` and covers the pure helpers like `getLineContext`, not the DOM construction). That is not a testing failure — it is a *consequence* of building the UI in a layer that needs a browser to exercise. The proposed frontend rewrite would not magically test the DOM either, but it would shrink the untested surface and let the genuinely logical parts (mutation patching, status derivation) move into testable plain functions.

**Performance is architecturally fine.** Startup is one `git diff` plus one JSON read; the metadata/lazy-hunk split already addressed the one real bottleneck (shipping all hunks at once). The watcher is a 500 ms poll of a single known file — negligible. `BlobSHAs` batches into one `git ls-tree`, avoiding an N+1 over marked files. No O(n²) baked into the data model. The only per-interaction git work is the deliberate, documented choice to *not* recompute on file selection. Nothing here needs changing.

---

The project is well-built and the recent refactors moved it in the right direction. The single highest-leverage move is removing GopherJS: it is the one decision that fights all three stated goals at once (small, self-contained, fast), and the type-sharing it provides is mostly illusory because the bridge is already JSON. Everything else is minor pruning.
