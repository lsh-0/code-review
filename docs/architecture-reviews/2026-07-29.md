# Architecture Review: code-review (frontend-weighted)

## Purpose

**A local GUI for leaving line-anchored comments on a branch-vs-main diff, persisted to a JSON
file that an AI agent can read and edit back.** Everything else — expansion, find, grouping,
banners — exists to make leaving and revisiting those comments fast.

## Structure

The frontend follows its own spec faithfully: a pure core (`ts/core`, ~800 lines) with no DOM or
bridge references, a typed RPC client (`ts/client.ts`), and a render layer (`ts/render` +
`ts/main.ts`, ~2,500 lines) that alone builds DOM. The layering is real and the core genuinely
pure — that part is sound and worth keeping verbatim.

The structural problem sits inside the render layer, and it has a name: **the DOM is a second
model.** `state.diffFiles` holds the parsed diff, but three features store their truth only in
the rendered tree:

- Expanded context lines are fetched and spliced into the DOM (`spliceRevealed`) without ever
  entering the diff model.
- Expansion frontier state lives in `Affordance` objects captured by DOM event closures.
- Comment mutations are applied by *patching* the tree in place (`mutate.ts` — querying
  `[data-line]`, replacing threads, rebuilding blocks) precisely because a re-render from the
  model would lose the expanded lines that exist nowhere else.

The current bug item is the direct bill for this: a comment on an expanded line orphans because
context capture reads the model while the user commented on a line that exists only in the DOM.
The planned fix's mid-flight navigation guards and affordance bookkeeping are further premiums on
the same policy. The model/DOM split also forces the callback plumbing: five callback-bag
interfaces (`CommentActions`, `DiffCallbacks`, `OverviewCallbacks`, `MutationContext`,
`ExpandContext`) are threaded through every render function to reach the same handful of modal
and mutation handlers wired once in `main.ts`.

A second, quieter duplication: **comment semantics are implemented twice.** `ts/core/comments.ts`
mirrors the Go model function-for-function (`isOutdated`, `currentLineNumber`,
`fileCommentStatus`, `commentRootLine` — each doc-commented "mirrors the Go X"), and
`ts/core/types.ts` re-declares the anchor history wire shape. Meanwhile the CLI (`backend/cli.go`)
already solves this correctly for agents: it sends *derived* fields (`Line`, `Outdated`) and keeps
the anchor machinery private. The GUI is the only consumer that receives raw anchors and
re-derives their meaning in a second language.

## Growth

Recent history (multi-select, in-page find, top-level comments, rename placeholders) is view
features over an unchanging domain — growth is toward the purpose, not away from it. But each
feature has paid the second-model tax: multi-select forced per-region scoping (`fileRegion`,
`cssEscape`); find is 375 lines that mutate the rendered tree with `<mark>`s and must tolerate
every other mutator; the pending auto-expansion must thread affordance handles out of
`renderFileHunks` and guard async splices against navigation. The TODO list is more of the same
shape (keyboard file navigation, ignore patterns, a controls bar, imported PR feedback), so the
tax compounds from here. No TODO cluster signals a module fighting its design — the fighting is
all in the render layer's mutation discipline.

## Proposed architecture: one model, disposable DOM

A refactor of the render layer's discipline, not a rewrite — core, client, and most DOM-building
functions survive.

1. **Slim the wire model.** The backend sends comments the way the CLI already does: current
   line, outdated flag, last good context — derived in Go, anchors never cross the bridge.
   Deletes most of `ts/core/comments.ts` (threading helpers remain), the anchor types in
   `types.ts`, and their tests. One implementation of comment semantics, in the language that
   owns the data. This is the pending change's Decision 1 (backend context capture) carried to
   its conclusion: the frontend stops knowing anchors exist.
2. **Move the DOM's hoarded state into the model.** Revealed lines become part of the per-file
   view state (merged into the file's line runs); expansion frontiers become plain `ExpandState`
   values in `state` keyed by file and gap — the pure arithmetic in `core/expand.ts` already
   exists and is untouched.
3. **Re-render regions, don't patch them.** Rendering a file section becomes a function of
   (file model, comments, expand state) → DOM, re-run wholesale for that region on any change:
   mutation, expansion, refresh. Pane scroll is the only DOM state to restore. This deletes the
   patching half of `mutate.ts`, the `Affordance` closures, and the planned navigation guards —
   an async fetch just updates state; if the file is no longer shown, there is no region to
   render, by construction.
4. **Let the callback bags go.** With rendering triggered centrally, the five interfaces
   collapse into direct imports or a single small dispatch function. The `currentFile`
   getter/setter shim over `selectedFiles` goes at the same time — pick the array and fix the
   call sites.

**What it removes:** the DOM-as-model concept (the root of this item's bug class), ~150 lines of
patching, five callback interfaces, the duplicated comment semantics (~200 lines plus tests), the
two-language anchor contract. Net on the order of 500 lines, but the concept count matters more:
after it, "add a view feature" touches one model and one render function.

**What it sharpens:** the pending auto-expansion becomes "compute needed reveals (pure — already
planned as task 3.3), fetch, merge into state, render once". The imported-PR-feedback TODO — the
most strategic item on the list — lands as comments arriving pre-derived from another backend
source, with zero frontend change to comment semantics.

**Honest costs:** find's `<mark>` highlights are wiped by a region re-render and must re-apply
(one hook after render); in-region text selection is lost on mutation (minor); a mutation
re-highlights the whole region rather than one thread — per-line `highlightLine` over a large
file is the one place to watch, and caching by (content, language) is the ready answer.

## Reductions

- Backend sends derived comment placement; delete the TS mirror (`core/comments.ts` majority,
  anchor wire types, fixture pins for anchor shapes).
- Delete `mutate.ts` patching in favour of region re-render.
- Collapse the five callback-bag interfaces.
- Remove the `currentFile` compatibility accessor.
- **No feature cuts.** The feature set is well-distilled; every feature traces to the purpose or
  to a documented WebKitGTK gap (find, zoom are platform compensation). The bloat here is
  structural, not feature-level — worth saying plainly.

## Tests & performance

The suite is at the right altitude: core tests pin requirements (expansion arithmetic, threading,
status derivation), DOM tests assert on real trees, fixtures pin wire shapes. The proposal makes
it smaller and stronger at once: the patch-path branches in `mutate.ts` — currently needing their
own DOM tests for replace/insert/remove cases — disappear, and render tests reduce to
state-in/tree-out. The expansion state machine is the standing candidate for property tests
(converging affordances: frontiers never cross, revealed set is monotonic).

Performance shape is sound: lazy hunk fetches, one cached file body per revision backend-side,
mutations user-paced. Region re-render is O(file) per mutation but bounded and event-driven. The
one architectural watch item is the uncapped auto-reveal from the pending change: a comment far
from any hunk renders a very large region, and if that ever hurts, windowing the rendered lines
is the answer — which is only reachable *from* model-driven rendering. The proposal is the
precondition for that escape hatch, not in tension with it.
